# OmniGuard V2X v3.0.3 — Guarded PQC Key Rotation Foundation

## Status

This milestone extends the durable ML-DSA-44 / ML-KEM-512 identity work with a local operator-controlled rotation path and conservative provider-policy metadata. The canonical public release version remains `3.0.2` while v3.0.3 is under development.

This is a research hardening feature. It is not a production fleet key-management system, manufacturing PKI, HSM service, or safety-certified rotation mechanism.

## Local operator only

Rotation is exposed only through the opt-in native utility:

`smartcar_pqc_key_admin`

No HTTP, V2X, Go control API, sync protocol, dashboard, or other network endpoint can request PQC key rotation in this milestone.

The build target is disabled by default and must be explicitly enabled with:

`-DSMARTCAR_BUILD_PQC_KEY_ADMIN=ON`

Runtime/operator rotation also remains disabled unless:

`SMARTCAR_CPP_PQC_ROTATION_ENABLED=1`

## Operator flow

1. Inspect the current non-secret key metadata:

   `smartcar_pqc_key_admin inspect --identity <vehicle-id>`

2. Enter a maintenance window and set `SMARTCAR_CPP_PQC_ROTATION_ENABLED=1`.
3. Provide a written reason of 8–256 characters.
4. Confirm the exact active non-secret key identifier using:

   `--confirm ROTATE:<current-key-id>`

5. The utility validates the existing keystore before any key changes.
6. A protected encrypted backup of the previous keystore is created.
7. A replacement ML-DSA-44 / ML-KEM-512 identity is generated and validated at a staging path while the active keystore remains untouched.
8. A prepared rotation receipt is written.
9. The validated staging keystore is activated with an operating-system replacement primitive.
10. The active keystore is re-opened and cryptographically validated.
11. A completed receipt is written and linked to the prepared receipt with SHA3-256.

A wrong confirmation, disabled rotation policy, malformed current keystore, wrong wrapping key, staging validation failure, or unsupported provider policy fails closed before activation.

## Rotation evidence

The rotation evidence directory contains:

- an encrypted backup of the previous keystore;
- `OMNIGUARD_PQC_ROTATION_PREPARED_V1` receipt;
- `OMNIGUARD_PQC_ROTATION_COMPLETED_V1` receipt.

Receipts contain only operational metadata such as identity, provider, previous/new key IDs, reason, timestamps, and backup filename. They do not contain private keys, wrapping credentials, plaintext shared secrets, or PQC secret-key bytes.

The backup still contains encrypted historical private key material and therefore must be protected as sensitive cryptographic material. It is not claimed to be WORM storage or hardware-protected evidence.

If activation succeeds but the completed receipt cannot be persisted, the utility fails with an explicit message that rotation may already be active and requires operator inspection before further operation. The prepared receipt and protected backup remain the recovery evidence boundary.

## Provider metadata and hardware-required policy

Implemented provider:

- provider: `software_encrypted_file`
- hardware backed: `false`
- non-exportable: `false`
- local rotation supported: `true`

`SMARTCAR_CPP_PQC_HARDWARE_REQUIRED=1` is intentionally fail-closed because no TPM2, PKCS#11, or HSM-backed native PQC provider is implemented in this milestone. There is no simulated hardware-backed fallback.

`smartcar_pqc_key_admin provider-status` exposes only non-secret provider capabilities and enforces this policy.

## Validation

The hosted operator self-test verifies:

1. a valid durable keystore can be rotated locally;
2. a wrong exact-key confirmation is rejected without changing identity;
3. disabled rotation is rejected without changing identity;
4. a new key ID is activated after successful rotation;
5. the encrypted backup still validates as the previous identity;
6. prepared and completed receipts are generated and linked;
7. receipt metadata does not claim private-key exposure or remote rotation;
8. the software provider is reported as non-hardware-backed/exportable;
9. hardware-required policy rejects the software provider.

The normal v3.0.2 release identity, adversarial validation, software-HIL, incident-response, Go security/fuzz, real-liboqs native target, and package checksum gates remain in CI while v3.0.3 is developed.

## Deliberate limitations

This milestone does not yet provide:

- TPM2 / PKCS#11 / HSM key generation or non-exportable keys;
- remote enrollment or certificate authority integration;
- automatic/scheduled key rotation;
- remote rotation commands;
- a distributed validator approval ceremony for rotation;
- anti-rollback hardware counters;
- guaranteed WORM audit storage;
- automated historical-ledger trust migration across multiple key generations;
- ISO 26262 / ASIL certification or production vehicle approval.

Historical ledger verification across rotated identities must be treated as a separate trust-history/keyring problem rather than silently accepting any previous key. That is the next security design area after local rotation is validated.
