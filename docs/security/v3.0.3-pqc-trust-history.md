# v3.0.3 — Historical PQC Trust Keyring & Signed Key Transitions

## Scope

This milestone extends the durable native PQC identity foundation with an explicit, bounded historical trust model for ML-DSA-44 / ML-KEM-512 key generations.

The goal is narrow: after a controlled local key rotation, previously persisted native ledger blocks can continue to have their ML-DSA authenticity checked against an explicitly admitted historical public key rather than against the currently active private key only.

This is a research hardening feature. It is not a production automotive PKI, certificate authority, remote enrollment service, hardware root of trust, or vehicle-safety certification mechanism.

## Trust-keyring format

The local keyring format is:

`OMNIGUARD_PQC_TRUST_KEYRING_V1`

Properties:

- one self-signed root generation;
- ordered monotonically increasing generations;
- default maximum of 8 generations;
- absolute supported bound of 16 generations;
- no silent eviction when the bound is reached;
- no historical private keys stored in the keyring;
- exact ML-DSA-44 and ML-KEM-512 public keys recorded per generation;
- active generation and active key ID recorded explicitly;
- active key ID is compared to the durable encrypted keystore during inspection/verification;
- root and every transition are hash chained with SHA3-256.

## Root initialization

Root initialization is explicit and one-time:

```text
smartcar_pqc_trust_admin init --identity <vehicle-id>
```

The root record contains the current durable key ID and public ML-DSA / ML-KEM keys. The root statement is signed with the matching current ML-DSA private key.

If the keyring already exists, initialization refuses to overwrite it.

Deleting the keyring and creating a new trust root is not an automatic recovery path.

## Rotation and admission workflow

Key rotation remains a separate guarded local operator action through `smartcar_pqc_key_admin`.

After rotation, historical trust is not granted automatically. The operator must explicitly admit the transition using the encrypted previous-keystore backup generated by the rotation step:

```text
smartcar_pqc_trust_admin admit \
  --identity <vehicle-id> \
  --previous-keystore <encrypted-backup-path> \
  --reason <written-reason> \
  --confirm ADMIT:<active-key-id>
```

The transition statement binds:

- vehicle identity;
- previous generation;
- new generation;
- previous key ID;
- new key ID;
- new ML-DSA-44 public key;
- new ML-KEM-512 public key;
- SHA3-256 of the written reason;
- previous transition hash.

The same transition statement must verify under both:

1. the previous generation ML-DSA private key; and
2. the new generation ML-DSA private key.

This creates explicit proof that the previously trusted generation authorized the successor and that the successor key possessed its corresponding private material at admission time.

## Rollback and downgrade behavior

The keyring is verified as a complete ordered chain. The following conditions fail closed:

- duplicate key IDs;
- repeated or skipped generations;
- reordered transitions;
- missing transitions;
- changed transition hashes;
- changed public keys;
- invalid root self-signature;
- invalid previous-generation transition signature;
- invalid new-generation transition signature;
- generation count above the configured bound;
- configured generation bound differing from the initialized keyring;
- keyring active key ID differing from the current durable encrypted keystore.

The active durable key binding makes a copied older keyring fail verification after a successful rotation/admission because its head key no longer matches the currently active keystore.

This is local rollback detection. It is not TPM monotonic-counter attestation, secure-boot attestation, remote transparency logging, or WORM storage.

## Historical ledger verifier

`smartcar_pqc_history_verify` verifies persisted native JSON ledgers using:

- bounded file parsing;
- block index ordering;
- vehicle identity binding;
- previous-hash linkage;
- canonical telemetry hashing;
- event SHA-256 and SHA3-256 hashes;
- native block SHA3-256 recomputation;
- AES-256-GCM authentication/decryption of the persisted dual hash;
- exact dual-hash recomputation;
- ML-DSA-44 signature verification;
- exact trusted public-key matching from the verified keyring;
- PQC binding-hash recomputation;
- PQC digest recomputation.

For a block signed by the currently active generation, the verifier also re-runs ML-KEM-512 decapsulation with the active private KEM key and checks the persisted shared-secret hash.

For a historical generation, the verifier does **not** retain or recover the previous ML-KEM private key. Therefore:

- historical ML-DSA ledger authenticity can be verified;
- historical key membership can be verified through the signed transition chain;
- historical block/hash/linkage/AES-GCM integrity can be verified;
- historical ML-KEM shared-secret claims are **not** independently re-decapsulated.

The verifier reports this distinction explicitly and does not claim otherwise.

## Security boundaries

This milestone does not provide:

- real TPM2, PKCS#11, or HSM-backed non-exportable PQC keys;
- remote key enrollment;
- remote trust mutation;
- production PKI or certificate revocation;
- automatic rotation;
- automatic admission;
- silent historical key eviction;
- historical ML-KEM private-key escrow;
- hardware monotonic counters;
- formal verification;
- production or vehicle-safety certification.

## Operational order

Recommended local maintenance order:

1. initialize the trust root before the first rotation;
2. persist/validate the current ledger;
3. execute guarded local rotation;
4. preserve the encrypted previous-keystore backup;
5. explicitly admit old → new using the trust admin;
6. verify keyring head matches the active durable keystore;
7. verify historical ledgers with `smartcar_pqc_history_verify`;
8. retain rotation and trust evidence according to the research retention policy.

If admission fails after the durable keystore has already rotated, historical verification remains fail-closed until the trust state is repaired deliberately. The system does not automatically trust the new key or discard the old generation.
