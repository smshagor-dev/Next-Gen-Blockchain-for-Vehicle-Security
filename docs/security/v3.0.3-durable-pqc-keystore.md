# OmniGuard V2X v3.0.3 — Durable PQC Identity

## Status

v3.0.3 is the next security-hardening phase after v3.0.2 release readiness. The canonical public release version remains `3.0.2` until v3.0.3 release preparation is complete.

Milestone 1 introduced the durable native post-quantum keystore. Milestone 2 integrates that keystore into the supported native blockchain authority path so `RealPqcEngine` no longer generates a fresh process-local identity at startup.

## Problem addressed

The hardened v3.0.2 native target uses real liboqs ML-DSA-44 and ML-KEM-512, but its supported native engine previously generated a fresh signing/KEM identity on every process start. v3.0.3 replaces that process-ephemeral authority with persisted, vehicle-bound key material.

## Keystore format

Format identifier:

`OMNIGUARD_PQC_KEYSTORE_V1`

Provider metadata:

- provider: `software_encrypted_file`
- signature algorithm: `ML-DSA-44`
- KEM algorithm: `ML-KEM-512`
- hardware backed: `false`
- non-exportable: `false`

The provider deliberately does not claim TPM/HSM/PKCS#11 protection.

## Stored material

Plaintext metadata contains:

- format/provider identifiers;
- vehicle/keystore identity;
- stable key identifier derived with SHA3-256 from the identity and both public keys;
- ML-DSA-44 public key;
- ML-KEM-512 public key;
- algorithm identifiers.

Private ML-DSA and ML-KEM key material is wrapped using AES-256-GCM under the independent credential domain:

`SMARTCAR_CPP_PQC_KEYSTORE_KEY`

The authenticated-data binding includes the keystore format, identity, stable key ID, both algorithm identifiers, and the private-key role.

`SMARTCAR_CPP_PQC_KEYSTORE_KEY` must not be reused as `SMARTCAR_CPP_DATA_KEY`, authentication, consensus, recovery, hardware, V2X, storage, incident, forensic, or insurance credentials.

The supported native runtime also requires:

`SMARTCAR_CPP_PQC_KEYSTORE_PATH`

The path is explicit rather than silently selecting a hidden fallback location.

## Supported native authority integration

`RealPqcEngine` now consumes `PqcKeyMaterial` returned by `PqcKeyStore::load_or_create()`.

The supported native engine no longer calls `OQS_SIG_keypair` or `OQS_KEM_keypair`. Key generation is confined to the keystore first-create path. On subsequent starts, the engine loads the same ML-DSA-44 and ML-KEM-512 identity.

The keystore identity must equal the configured vehicle identity before genesis/signing authority is established.

The stable `pqc_key_id` is bound into:

- the in-memory PQC artifact;
- PQC message construction;
- shared-secret hashing;
- PQC artifact binding hash;
- block PQC digest;
- persisted native ledger output.

This prevents the durable identity identifier from being treated as detached display-only metadata.

## Fail-closed behavior

When the configured keystore path does not exist, the software provider generates one ML-DSA-44 keypair and one ML-KEM-512 keypair and publishes the keystore with an atomic temporary-file rename.

When the path already exists, the provider never silently regenerates identity. It validates and loads the existing file. The operation fails closed when any of the following occurs:

- malformed/truncated JSON;
- missing or unexpected schema fields;
- unsupported format/provider/algorithm identifiers;
- vehicle/keystore identity mismatch;
- public-key/key-ID mismatch;
- AES-GCM authentication/tag failure;
- wrong wrapping credential;
- unexpected key lengths;
- ML-DSA public/private inconsistency;
- ML-KEM public/private inconsistency;
- symlinked keystore path;
- invalid file size/type.

Private key buffers are cleansed on destruction/move replacement using `OPENSSL_cleanse`. This remains a software-memory boundary and is not equivalent to non-exportable hardware keys.

## Validation

The standalone keystore self-test verifies:

1. initial identity creation;
2. reload preserves the exact key ID and public keys;
3. provider metadata remains truthful;
4. modified AES-GCM authentication tag is rejected;
5. wrong wrapping key is rejected;
6. truncated keystore is rejected instead of regenerated;
7. restored original keystore reloads the same identity.

The supported `smartcar_blockchain --self-test` additionally verifies the integration boundary:

1. normal AES-256-GCM and full-chain checks still pass;
2. native blockchain construction creates/loads the configured keystore;
3. reconstructing the blockchain with the same vehicle/path/key preserves the same PQC key ID;
4. opening the same keystore with a wrong wrapping key fails closed.

CI supplies a per-run isolated keystore path and uses the same pinned real-liboqs profile as the hardened native target.

## Remaining v3.0.3 work

- add an explicit local operator-controlled key rotation/provisioning workflow rather than silent rollover;
- define durable identity migration/backup behavior;
- expose conservative non-secret provider/key-ID metadata to runtime capability reporting;
- add hardware-required fail-closed policy hooks for future TPM2/PKCS#11/HSM providers;
- complete v3.0.3 release metadata, changelog, and release-readiness gates only after the security work is green.

## Security boundary

This phase provides encrypted software persistence, vehicle-bound durable PQC identity, and fail-closed validation. It does not provide hardware-backed/non-exportable keys, remote enrollment/PKI, secure manufacturing provisioning, anti-rollback hardware counters, formal verification, ISO 26262/ASIL certification, or production fleet approval.
