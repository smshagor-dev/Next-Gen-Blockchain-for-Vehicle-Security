# OmniGuard V2X v3.0.3 — Durable PQC Identity Foundation

## Status

This branch begins the next security-hardening phase after the v3.0.2 release-readiness work. The canonical public release version remains `3.0.2` until v3.0.3 release preparation is complete.

Milestone 1 introduces and validates a durable native post-quantum keystore. It does **not yet switch `RealPqcEngine` authority** from process-ephemeral key generation to the persisted keystore; that wiring is the next milestone in the same phase.

## Problem addressed

The hardened v3.0.2 native target uses real liboqs ML-DSA-44 and ML-KEM-512, but `RealPqcEngine` currently generates a fresh signature/KEM identity on every process start. That is suitable for cryptographic primitive validation but not for a durable vehicle identity.

v3.0.3 establishes the storage and provisioning boundary required to make that identity persistent without silently regenerating keys after corruption or credential loss.

## Keystore format

Format identifier:

`OMNIGUARD_PQC_KEYSTORE_V1`

Provider metadata:

- provider: `software_encrypted_file`
- signature algorithm: `ML-DSA-44`
- KEM algorithm: `ML-KEM-512`
- hardware backed: `false`
- non-exportable: `false`

The provider deliberately does not claim TPM/HSM/PKCS#11 protection.

## Stored material

Plaintext metadata contains:

- format/provider identifiers;
- vehicle/keystore identity;
- stable key identifier derived with SHA3-256 from the identity and both public keys;
- ML-DSA-44 public key;
- ML-KEM-512 public key;
- algorithm identifiers.

Private ML-DSA and ML-KEM key material is wrapped using AES-256-GCM under an independent credential domain:

`SMARTCAR_CPP_PQC_KEYSTORE_KEY`

The authenticated-data binding includes the keystore format, identity, stable key ID, both algorithm identifiers, and the private-key role.

`SMARTCAR_CPP_PQC_KEYSTORE_KEY` must not be reused as `SMARTCAR_CPP_DATA_KEY`, authentication, consensus, recovery, hardware, V2X, storage, incident, forensic, or insurance credentials.

## Fail-closed behavior

When the configured keystore path does not exist, the software provider generates one ML-DSA-44 keypair and one ML-KEM-512 keypair and publishes the keystore with an atomic temporary-file rename.

When the path already exists, the provider never silently regenerates identity. It validates and loads the existing file. The operation fails closed when any of the following occurs:

- malformed/truncated JSON;
- missing or unexpected schema fields;
- unsupported format/provider/algorithm identifiers;
- identity mismatch;
- public-key/key-ID mismatch;
- AES-GCM authentication/tag failure;
- wrong wrapping credential;
- unexpected key lengths;
- ML-DSA public/private inconsistency;
- ML-KEM public/private inconsistency;
- symlinked keystore path;
- invalid file size/type.

Private key buffers are cleansed on destruction/move replacement using `OPENSSL_cleanse`. This remains a software-memory boundary and is not equivalent to non-exportable hardware keys.

The module is compiled with the hardened native target immediately so build regressions are caught even before authority switches to it.

## Validation

The native self-test creates a temporary keystore and verifies:

1. initial identity creation;
2. reload preserves the exact key ID and public keys;
3. provider metadata remains truthful;
4. modified AES-GCM authentication tag is rejected;
5. wrong wrapping key is rejected;
6. truncated keystore is rejected instead of regenerated;
7. restored original keystore reloads the same identity.

CI builds this target with the same pinned real liboqs profile used by the hardened native blockchain target.

## Next milestone

Milestone 2 will explicitly wire `RealPqcEngine` to `PqcKeyStore`:

- require `SMARTCAR_CPP_PQC_KEYSTORE_KEY` for the supported native target;
- choose a confined keystore path;
- bind the keystore identity to the configured vehicle identity;
- load-or-create before genesis/signing authority is established;
- remove process-ephemeral keypair generation from the supported path;
- expose non-secret key ID/provider metadata;
- add restart persistence and tamper/wrong-key tests through `smartcar_blockchain --self-test`;
- keep hardware-required mode fail-closed until a real TPM2/PKCS#11/HSM provider exists.

## Security boundary

This milestone provides encrypted software persistence and fail-closed validation for PQC identity material. It does not provide hardware-backed keys, remote enrollment/PKI, secure manufacturing provisioning, anti-rollback hardware counters, formal verification, ISO 26262/ASIL certification, or production fleet approval.
