# OmniGuard V2X v3.0.2 Final Release Checklist

This checklist separates automated release evidence from explicit operator publication actions.

## Automated gates before publication

- [x] Canonical `VERSION` is `3.0.2`.
- [x] CMake project version matches `3.0.2`.
- [x] Python release/security capability metadata matches `3.0.2`.
- [x] Go release version constant matches `3.0.2`.
- [x] Public release `v3.0.2` maps explicitly to internal hardening phase `v3.2`.
- [x] Release notes and changelog are present.
- [x] Full Python security regression suites pass.
- [x] Deterministic adversarial, software-HIL, and incident-response scenarios pass.
- [x] Hardened native target fails closed without real liboqs.
- [x] Historical legacy C++ demo remains isolated from the supported native target.
- [x] Pinned liboqs 0.16.0 native build passes.
- [x] AES-256-GCM / ML-DSA-44 / ML-KEM-512 native self-test passes.
- [x] Go security tests, bounded fuzz campaigns, and Go build pass.
- [x] Release-integrity manifest generation and self-verification pass on the validated release head.
- [x] Linux validation binaries and `SHA256SUMS` are produced and verified by CI.
- [x] Security Baseline runs on pushes to `main`, so the exact post-merge release commit receives full validation and commit-bound artifacts before tagging.
- [x] Publication workflow accepts the `v3.0.2` tag push and guarded tag-ref manual dispatch, while retaining exact-tag/exact-main checks.
- [x] Publication workflow requires the tagged SHA to equal the fetched `origin/main` SHA, not merely an older ancestor of `main`.
- [x] Validation/build/package job has read-only repository contents permission; only the dependent publish job receives `contents: write` after validation succeeds.
- [x] Guarded local tag operator script requires an explicit `--push` mutation mode and provides a non-mutating `--check-only` mode.
- [x] GitHub-native manual tag workflow requires explicit `CREATE-v3.0.2` confirmation and refuses tagging unless the exact current `main` commit has a successful push-triggered Security Baseline run.
- [x] GitHub-native tag workflow explicitly dispatches the publication workflow on the new tag ref instead of relying on recursive workflow triggering from a `GITHUB_TOKEN` tag push.

Any source change after these checks requires the complete release gate to run again because the source-integrity manifest is commit-bound.

## Required operator actions after final release PR merge

Do not create the public tag from an unmerged feature/release branch or from an older `main` ancestor.

1. Verify the exact current `main` commit contains `VERSION=3.0.2`, the expected release notes, `.github/workflows/release-v3.0.2.yml`, `.github/workflows/create-v3.0.2-tag.yml`, and the `main` push trigger in `.github/workflows/security-baseline.yml`.
2. Require the `Security Baseline` workflow triggered by that exact `main` push/merge commit to complete successfully. A successful PR-head run is not a substitute because the release-integrity manifest is commit-bound.
3. Confirm no newer commit landed on `main` after that successful run.
4. Choose one explicit tag-creation path:

   **Recommended GitHub-native path**

   - Open Actions → `Create OmniGuard V2X v3.0.2 Tag`.
   - Run the workflow from the default branch.
   - Enter exactly `CREATE-v3.0.2` as the confirmation input.
   - The workflow independently verifies exact `main`, the successful push-triggered Security Baseline, tag/release absence, creates the annotated `v3.0.2` tag, and explicitly dispatches `Publish OmniGuard V2X v3.0.2` on that tag ref.

   **Local operator path**

   ```bash
   bash scripts/create_v3_0_2_tag.sh --check-only
   bash scripts/create_v3_0_2_tag.sh --push
   ```

   A locally pushed tag is expected to trigger the publication workflow through the normal tag-push event.

5. Observe the `Publish OmniGuard V2X v3.0.2` workflow and require every validation/build/package step to pass.
6. Confirm the workflow-created GitHub Release points to the same tagged commit and includes the expected manifest, `SHA256SUMS`, validation binaries, and validation reports.
7. Verify the published artifact hashes against the attached `SHA256SUMS`.
8. Do not upload `.env`, local configuration, private keys, credentials, sensitive runtime logs, or unreviewed build directories.
9. Keep historical credential-rotation/history-rewrite work tracked separately; this release does not make previously exposed credentials safe again.

See `docs/releases/v3.0.2-postmerge-validation.md` for the post-merge validation boundary.

## GitHub-native tag operator safeguards

The manually dispatched `.github/workflows/create-v3.0.2-tag.yml` workflow:

- has no automatic push/tag trigger;
- requires exact confirmation text `CREATE-v3.0.2`;
- checks out current `main` and fetches `origin/main` plus tags;
- requires local checkout SHA to equal the exact fetched `origin/main` SHA;
- requires `VERSION=3.0.2` and the publication/security workflows to exist;
- queries `Security Baseline` push runs for `main` and requires a completed successful run whose `headSha` exactly equals the current `main` SHA;
- refuses an existing local/remote `v3.0.2` tag;
- refuses an existing `v3.0.2` GitHub Release;
- creates an annotated tag only after all checks pass;
- pushes only `refs/tags/v3.0.2`;
- verifies the local annotated tag resolves back to the intended `main` commit;
- explicitly dispatches `release-v3.0.2.yml` with `--ref v3.0.2`, because the workflow does not rely on a `GITHUB_TOKEN`-originated tag push to recursively trigger publication.

## Publication workflow safeguards

The `.github/workflows/release-v3.0.2.yml` workflow:

- accepts the `v3.0.2` tag push and a manual dispatch on the `v3.0.2` tag ref;
- rejects any execution whose `GITHUB_REF_TYPE` is not `tag` or whose ref name is not `v3.0.2`;
- fetches `origin/main` and requires the tagged SHA to equal the exact fetched `main` SHA;
- verifies the checkout exactly matches the tag commit SHA;
- verifies the publication workflow exists in the tagged source tree;
- runs validation/build/package with repository contents read-only;
- passes only the validated publication payload to a dependent publish job;
- grants `contents: write` only to the publish job after validation succeeds;
- re-verifies `SHA256SUMS`, release version, tag, and manifest commit binding after the job boundary;
- refuses to overwrite an existing `v3.0.2` GitHub Release;
- reruns release identity, integrity, security, native PQC, Go, fuzz, HIL, adversarial, and incident-response validation;
- regenerates the release-integrity manifest for the exact tag commit;
- rebuilds validation binaries from the tag commit;
- generates and verifies `SHA256SUMS` before publication;
- publishes the prepared release notes and validation evidence only after all prior steps pass.

## Guarded local tag operator safeguards

`scripts/create_v3_0_2_tag.sh`:

- refuses any mode except `--check-only` or `--push`;
- requires the current branch to be `main`;
- requires a clean working tree and index;
- requires `VERSION=3.0.2` and the publication workflow to exist;
- fetches `origin/main` plus tags before deciding eligibility;
- requires local `HEAD` to equal `origin/main` exactly;
- refuses an existing local or remote `v3.0.2` tag;
- checks that the publication workflow contains the exact-main runtime guard;
- performs no tag mutation in `--check-only` mode;
- creates an annotated `v3.0.2` tag only in explicit `--push` mode;
- removes the local tag if the remote push fails, avoiding ambiguous local state.

## Tag and artifact policy

- Expected tag: `v3.0.2`
- Canonical version: `3.0.2`
- Internal engineering phase: `v3.2`
- Supported native validation profile: OpenSSL AES-256-GCM + real liboqs ML-DSA-44 / ML-KEM-512
- Historical `smartcar_blockchain_legacy_demo`: lab/compatibility only, not a release security binary

A tag or binary built from a different commit must receive a new integrity manifest. Do not reuse a manifest across commits.

## Security / safety boundary

Passing this checklist establishes reproducible release identity and validation evidence for the research implementation. It does not establish production automotive certification, ISO 26262/ASIL compliance, formal verification, fleet-scale operational approval, or immunity from all attacks.
