# OmniGuard V2X v3.0.2

**Release:** `v3.0.2`  
**Internal hardening phase:** `v3.2`  
**Release type:** Research security hardening  
**Primary focus:** Native cryptographic modernization and real post-quantum validation

## Overview

v3.0.2 consolidates the native C++ security work into a publishable release identity. The supported native target uses authenticated encryption for protected persisted data, requires real liboqs post-quantum primitives, and excludes the historical XOR/simulated-PQC implementation from the supported executable.

This release also introduces a canonical repository version source so Python metadata, Go build metadata, and CMake configuration cannot silently diverge from the public release number.

## Native Cryptography

### AES-256-GCM

The supported native C++ path uses AES-256-GCM with a random nonce, authentication tag, and associated authenticated data. Modified authentication tags are rejected during the native self-test.

### Real Post-Quantum Operations

The supported native target uses real liboqs implementations of:

- ML-DSA-44 for signatures;
- ML-KEM-512 for key encapsulation.

The hardened target fails closed when a usable real liboqs target is unavailable. The CI source-build path is pinned to liboqs 0.16.0 / the repository-pinned commit.

### Legacy Isolation

The historical `blockchain.cpp` implementation remains available only through the explicitly named `smartcar_blockchain_legacy_demo` target. It is outside the supported v3.0.2 security build profile.

## Release Identity

`VERSION` is the public source of truth and contains `3.0.2`.

Release identity is aligned across:

- repository `VERSION`;
- CMake `PROJECT_VERSION`;
- Python `release_metadata.py`;
- security capability metadata;
- Go build version constant;
- CI regression tests.

The engineering documents retain `v3.2` as the internal hardening-phase name. This is intentionally exposed as metadata rather than hidden or rewritten.

## Hosted Validation

The v3.0.2 release gate retains and executes the complete Security Baseline, including:

- Python security regression suites;
- deterministic adversarial validation;
- deterministic software-HIL scenarios;
- deterministic incident-response scenarios;
- forced-no-liboqs fail-closed CMake validation;
- isolated legacy C++ demo build;
- pinned real-liboqs native C++ build;
- secure native crypto self-test;
- AES-256-GCM tamper rejection;
- ML-DSA-44 sign/verify validation;
- ML-KEM-512 encapsulation/decapsulation validation;
- full native chain verification;
- Go security tests;
- bounded Go fuzz campaigns;
- Go backend build;
- release-version drift regression checks.

## Compatibility Notes

- The supported native target requires OpenSSL 3.x and real liboqs.
- Simulated PQC is not a supported security fallback.
- The legacy C++ demo target is opt-in and must not be presented as equivalent to the supported native security target.
- Existing Python/Go research components continue to retain their documented hybrid-security and consensus limitations.

## Security Boundary

This release materially improves implementation integrity and downgrade resistance, but it does not claim:

- production automotive cryptographic certification;
- ISO 26262 / ASIL certification;
- formal verification;
- complete TPM/HSM-backed non-exportable key deployment;
- fleet-scale operational certification;
- immunity from all cyberattacks.

Historically exposed repository credentials must still be rotated and any approved Git-history cleanup remains an operational task outside this release.
