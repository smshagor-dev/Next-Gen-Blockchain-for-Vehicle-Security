# OmniGuard V2X v3.0.3

## Durable PQC Identity, Historical Trust & Runtime Recovery Hardening

v3.0.3 consolidates the post-v3.0.2 native hardening work into a release candidate focused on durable post-quantum identity lifecycle, mixed-generation ledger verification, local rollback detection, recovery safety, and supply-chain evidence.

This remains a **research hardening release**. It is not production-certified, vehicle-safety-certified, formally verified, or a substitute for an OEM PKI/HSM deployment.

## Native PQC identity lifecycle

- Durable encrypted ML-DSA-44 / ML-KEM-512 keystore.
- AES-256-GCM protection for software-stored private PQC material.
- Stable key identifiers across process restarts.
- Guarded local rotation with encrypted previous-keystore backup.
- Explicit operator confirmation; no remote rotation endpoint.
- Signed old-to-new ML-DSA transition evidence.
- Bounded historical public-key trust keyring with no silent generation eviction.

## Mixed-generation native runtime

The supported `smartcar_blockchain` target now uses the v3.0.3 persisted runtime path.

It can:

- initialize a new native ledger;
- load and verify a persisted ledger;
- append only after the existing ledger verifies;
- authenticate active-generation ML-DSA and ML-KEM claims;
- verify admitted historical ML-DSA generations through the signed trust keyring;
- append new active-generation blocks to an admitted historical chain;
- report `ACTIVE_ONLY` or `MIXED_GENERATION_VERIFIED` migration state.

Historical ML-KEM private keys are intentionally not retained. Therefore an old generation's ML-DSA ledger authenticity is verifiable, but its historical ML-KEM shared-secret claim is **not independently re-decapsulated**. The runtime reports this boundary explicitly.

## Rollback and recovery state

v3.0.3 adds `OMNIGUARD_PQC_ROLLBACK_ANCHOR_V1`, a locally authenticated state anchor that binds:

- vehicle identity;
- monotonic software sequence/generation;
- active PQC key ID;
- signed trust-keyring head hash;
- previous anchor hash.

The state admin validates consistency before allowing an anchor initialize/advance operation and can check an encrypted previous keystore as an admitted historical recovery candidate. Historical restoration is never automatic.

The current anchor is **not a hardware monotonic counter** and is not externally immutable. If an attacker can roll back the anchor, keystore, and trust keyring together, this local mechanism alone cannot prove rollback. TPM monotonic counters, HSM-backed state, WORM storage, or remote transparency checkpoints remain deployment-level future work.

## Provider policy

`SMARTCAR_CPP_PQC_PROVIDER` recognizes explicit policy names:

- `software_encrypted_file` — implemented software provider;
- `tpm2` — declared but not implemented;
- `pkcs11` — declared but not implemented;
- `hsm` — declared but not implemented.

Requesting an unavailable hardware provider fails closed. `SMARTCAR_CPP_PQC_HARDWARE_REQUIRED=1` also rejects the software provider. There is no simulated hardware-backed fallback and no claim that software keys are non-exportable.

## Legacy and deterministic behavior

- Historical C++ XOR/simulated-PQC demo source is removed from the supported repository build path.
- The supported native build requires real liboqs.
- Smart-contract mock receipt IDs now use deterministic SHA-256 instead of Python's randomized `hash()`.
- Remote smart-contract connector results are labelled `remote_rpc` and require an explicit successful transaction identifier before reporting success.

## Supply-chain evidence

Release validation generates:

- commit-bound source-integrity manifest;
- deterministic repository-declared SBOM;
- non-secret build provenance;
- current-tree prohibited-secret scan;
- SHA-256 checksums for publication artifacts;
- adversarial validation report;
- software-HIL security report;
- incident-response validation report.

Dependency pins include liboqs 0.16.0 at the repository-pinned commit and nlohmann/json 3.11.3 with SHA-256 archive verification. Hosted validation can enforce the expected GCC 13.3.x toolchain family.

## Credential and history boundary

`SMARTCAR_CPP_PQC_ROLLBACK_KEY` is an independent credential domain and must not reuse the PQC wrapping key, data key, API credentials, validator credentials, incident keys, or recovery keys.

Current-tree scanning prevents newly tracked local environment/private-key files and known prohibited legacy secret declarations. Previously exposed credentials in historical Git commits must still be rotated and, if the owner approves a coordinated rewrite, removed from repository history separately. This release does not automatically rewrite shared Git history.

## Release Integrity Evidence

The publication workflow is guarded to the exact `v3.0.3` tag target and requires that target to equal the exact current `main` commit. It re-runs the full release validation suite, regenerates the commit-bound integrity manifest, SBOM, provenance, reports and SHA-256 checksums from the tagged commit, and refuses an existing release.

Artifacts are research validation evidence, not production-certified automotive binaries.

## Security boundary

v3.0.3 improves fail-closed behavior and evidence quality but does not claim:

- absence of vulnerabilities;
- protection from an authorized malicious validator supermajority;
- production PKI/enrollment governance;
- real TPM2/PKCS#11/HSM private-key custody;
- hardware monotonic rollback resistance;
- certified vehicle actuation safety;
- formal verification or regulatory certification.
