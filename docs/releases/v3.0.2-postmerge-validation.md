# OmniGuard V2X v3.0.2 Post-Merge Validation

This document defines the final release-candidate validation boundary after release-preparation changes are merged into `main` and before the public `v3.0.2` tag is created.

## Required invariant

The repository Security Baseline must execute on every push to `main`.

This ensures the exact merge commit selected for release receives the same full validation stack used on release/security branches, including:

- canonical release identity checks;
- release-integrity manifest generation and verification;
- Python security regression suites;
- deterministic adversarial validation;
- software-HIL security scenarios;
- incident-response validation;
- fail-closed native configuration without liboqs;
- isolated legacy C++ demo build;
- pinned real-liboqs native build;
- AES-256-GCM / ML-DSA-44 / ML-KEM-512 native self-test;
- Go security tests and bounded fuzz campaigns;
- Linux validation binary packaging;
- SHA-256 checksum verification;
- validation-report artifact upload.

## Publication sequence

1. Merge all v3.0.2 release-readiness changes into `main`.
2. Require the Security Baseline push workflow for that exact `main` commit to complete successfully.
3. Confirm no newer commit has landed on `main`.
4. Run `bash scripts/create_v3_0_2_tag.sh --check-only`.
5. Only then use the explicit `--push` mode to create and push `v3.0.2`.
6. Require the tag-triggered publication workflow to re-run the complete release validation and publish only after all gates pass.

A successful PR-head run is not a substitute for the post-merge `main` run because the release-integrity manifest is commit-bound.

## Security boundary

This post-merge validation improves release traceability and reduces merge-resolution/version-drift risk. It does not establish production automotive certification, ISO 26262/ASIL compliance, formal verification, or immunity from all attacks.
