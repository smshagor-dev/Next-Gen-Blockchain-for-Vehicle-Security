# v4.0.0 Major Changes

## 1. Source-Backed Runtime Security Strength

v4.0.0 replaces the dashboard's legacy optional numeric **Security Score** presentation with a deterministic **Security Strength** posture.

The runtime does **not** invent a percentage score.

The live posture is derived from authenticated runtime state, explicit alert severity, and availability of core security metadata.

Supported states:

- **STRONG** — authenticated runtime connected, core security metadata available, and no explicit warning/high-risk signal
- **GUARDED** — partial connectivity or explicit warning/medium severity signal
- **DEGRADED** — authenticated runtime unavailable or required core security evidence is missing
- **RISK** — explicit high/critical/risk severity signal is present

The Security Strength result is:

- source-backed
- categorical rather than fabricated numeric scoring
- intentionally conservative
- not a certification or formal proof
- shared with the vehicle risk visualization

The vehicle risk indicator maps the same runtime posture to:

- green **PROTECTED**
- yellow **WARNING**
- red **RISK**

# v3.0.3 — Durable PQC Identity, Historical Trust & Runtime Recovery Hardening

v3.0.3 added durable post-quantum identity lifecycle and release-integrity infrastructure.

## Durable PQC keystore

Implemented capabilities include:

- durable encrypted ML-DSA-44 / ML-KEM-512 identity keystore
- AES-256-GCM protection of software-stored private PQC material
- stable key identifiers across restarts
- guarded local key rotation
- encrypted previous-keystore backups
- signed old-to-new ML-DSA transition evidence
- bounded historical public-key trust keyring
- explicit operator-controlled rotation
- no remote key-rotation endpoint

## Mixed-generation ledger verification

The runtime supports:

- active-generation ML-DSA verification
- admitted historical ML-DSA verification
- new active-generation blocks appended to approved historical chains
- rejection of unadmitted historical identity generations
- migration state reporting:
  - `ACTIVE_ONLY`
  - `MIXED_GENERATION_VERIFIED`

Historical ML-KEM private keys are intentionally not retained.

Therefore historical ML-KEM shared-secret claims are not independently re-decapsulated; this limitation is explicitly reported.

## Authenticated rollback/recovery state

v3.0.3 introduced:

```text
OMNIGUARD_PQC_ROLLBACK_ANCHOR_V1
```

The rollback state can bind:

- vehicle identity
- software sequence/generation
- active PQC key ID
- signed trust-keyring head
- previous anchor hash

Recovery is never automatic.

The current anchor is software-authenticated and does not claim hardware monotonicity or external immutability.

## PKCS#11 v3.2 PQC provider

v3.0.3 includes an opt-in PKCS#11 v3.2 provider adapter for ML-DSA-44 / ML-KEM-512.

Runtime hardware-backed claims require evidence for:

- real PKCS#11 v3.2 interface
- hardware slot/token
- ML-DSA mechanisms
- ML-KEM mechanisms
- non-extractable private keys
- sensitivity/non-exportability attributes
- non-exportable ML-KEM derived-secret handling
- SHA3-256 commitment/digest operations
- runtime provider probe verification

The implementation is source/ABI validated against canonical OASIS PKCS#11 v3.2 headers.

No production HSM/token custody claim is made without actual compatible hardware evidence.

Provider status:

- `software_encrypted_file` — implemented
- `pkcs11` — implemented and opt-in
- `tpm2` — recognized, concrete runtime adapter unavailable
- `hsm` — recognized, generic runtime adapter unavailable

Explicit unavailable hardware-provider requests fail closed.

v3.0.3 added:

The bootstrap:

- creates independent high-entropy credentials
- preserves existing non-empty credentials by default
- supports explicit `--rotate-all`
- never prints generated secret values
- keeps `.env` local and ignored
- keeps insecure defaults disabled
